# DAIN 보안 아키텍처 — Zero Trust / Default Deny (2026-10-25)

최상위 목표: 누구나 자신의 남는 컴퓨팅 자원을 쉽고 안전하게 공유할 수 있는
범용 분산 AI 시스템. 보안은 개발 완료 후 추가하는 기능이 아니라 시스템의
기본 구조다. 이 문서는 원칙, 현재 구현 상태, 위협 모델, 그리고 아직
보장하지 못하는 것을 구분해 기록한다. "보안이 완벽하다"는 선언은 하지 않는다.
각 주장 뒤에는 검증 방법(테스트·코드 위치)을 적는다.

## 0. 원칙

1. **Zero Trust**: 네트워크 위치·과거 이력·자기 신고를 신뢰하지 않는다.
   모든 요청은 신원(Peer ID), 권한(토큰/allowlist), 범위(자원 상한)를
   그 요청 시점에 검증한다.
2. **Default Deny**: 허용 목록에 없으면 거부한다. 빈 allowlist는 차단이다
   (2026-10-25 Relay 수정). 기본 자원 기여량은 0%다
   (제품 원칙 4 — 단, 현재 기본값 10%는 **위반, P0 수정 대상**).
3. **등록과 연산 권한의 분리**: 노드 등록(존재를 알림)과 연산 배정(작업을
   맡김)은 서로 다른 권한이다. 등록됐다고 연산이 허용되는 것이 아니다.
4. **사용자 승인 없는 연산 배정 금지**: 모델 다운로드·연산 실행은 사용자가
   허용한 범위 안에서만 일어난다. 현재 코드는 이 원칙을 **위반**한다
   (서비스 할당 시 백그라운드 자동 복제 — 제품 원칙 5 위반, P0).
5. **최소 권한·명시 범위**: 권한은 자원별(CPU/GPU/RAM/스토리지/네트워크)로
   나누고, 상한을 숫자로 적는다. 상한을 강제할 수 없으면 강제되는 것처럼
   말하지 않는다 (`limits` 패키지의 honest reporting 참조).
6. **격리**: 신뢰되지 않은 작업은 로컬 파일·자격증명과 격리한다. 원격 임의
   명령 실행은 금지한다. DAIN 프로토콜에는 셸·명령 실행 경로가 없다.
7. **즉시 중단·철회**: 사용자는 언제든 기여를 중단하고 권한을 철회할 수
   있어야 한다. 철회는 재시작을 기다리는 문서가 아니라 동작하는 절차다.
8. **실패의 정직성**: 지원하지 못하는 격리 기능은 자동 비활성화하고 그
   사실을 표시한다. 강제되지 않는 한도를 강제되는 것처럼 보고하지 않는다.

## 1. 신원과 인증 — 현재 상태

| 요소 | 현재 상태 | 근거 |
|---|---|---|
| 노드 신원 | Ed25519 키 → libp2p Peer ID. 키는 `~/.distributed-ai-node/identity.key` (0700 dir, 0600 file) | `node/internal/identity` |
| 전송 보안 | libp2p Noise/TLS 암호화 전송. Peer ID는 전송 계층에서 인증됨 | go-libp2p 기본 |
| ResourceInfo V2 신원 | payload `peer_id` == 연결의 인증된 `RemotePeer`가 아니면 ACK 거부 + 미전달 | `node/internal/p2p/p2p.go`, `TestResourceV2RejectsSpoofedPeerID` |
| Relay 접근 | Peer ID allowlist ACL. 예약·회선 양단에서 검사 | `node/internal/p2p/relay.go`, `TestRelayACLDeniesRogue` |
| Relay 기본값 | **빈 allowlist = 거부** (2026-10-25 수정). allow-all은 명시적 `--allow-all` 옵트인, 로컬 테스트 전용 | `TestRelayDefaultDeniesEmptyAllowlist` |
| 서비스 API | 노드 등록·하트비트는 API 키로 인증 (공유 테스트 키, TEST_FUND) | `service/internal/api` |
| 모델 무결성 | 매니페스트 SHA-256 + 청크별 SHA-256 검증, 불일치 시 조립 중단 | `node/internal/materialize` |

### 미해결 (신원·인증)
- 서비스 API 키는 공유 키다. 노드별 키·스코프 분리, 키 철회 목록이 없다.
  키가 유출되면 해당 키를 쓰는 모든 노드가 영향을 받는다.
- Relay allowlist는 정적이다. 철회는 파일 수정 + 릴레이 재시작으로만
  가능하고(§5 절차), 진행 중인 회선을 원격에서 즉시 끊는 온라인 철회는 없다.
- 원격 증명(remote attestation)이 없다. 노드 운영자가 자기 노드에서
  무엇이 실행됐는지 거짓으로 보고하는 것을 막을 수 없다 (하드웨어
  TEE가 없는 일반 사용자 기기에서는 원칙적으로 불가능 — §6 참조).

## 2. 자원 권한과 강제 — OS별 실태

`limits` 패키지(`limits/limits.go`)가 유일한 진실의 원천이다. 강제할 수
없으면 `Unenforced` + 사유를 보고하고, 강제되는 것처럼 말하지 않는다.

| 자원 | Linux | macOS | Windows |
|---|---|---|---|
| CPU 상한 | cgroup v2 `cpu.max` (quota/period) — 실제 강제. `limits.Apply`가 엔진 PID를 cgroup에 넣는다. 불가 시 Unenforced 보고 | **강제 없음**. cgroup이 없다. 스레드 수 힌트만. `limits.Apply`는 Unenforced를 보고한다 | **강제 없음**. Job Objects 미구현. 스레드 수 힌트만 |
| RAM 상한 | cgroup v2 `memory.max` — 실제 강제 (초과 시 해당 cgroup 내 OOM만 발생) | 강제 없음 | 강제 없음 |
| 스토리지 상한 | 모델 디렉토리 바이트 예산: 예산 초과 시 materialize 거부 (`MaxBytes` 검사). 디스크 전체 격리는 아님 | 동일 (예산 검사만) | 동일 |
| GPU | **어디에도 분수 강제 없음**. 벤더가 분수 연산 상한을 노출하지 않는다. `CUDA_VISIBLE_DEVICES`는 장치 전체 선택일 뿐이다. GPU 공유는 장치 전체 할당으로만 의미가 있다 | 동일 (Metal 분수 상한 없음) | 동일 |
| 네트워크 | Relay 회선당 16 MiB·서버 전체 구조적 상한 512 MiB (32회선). 노드별 대역폭 계량·차단은 없음 | 동일 | 동일 |
| 프로세스 수 | cgroup `pids.max`은 DAIN이 현재 설정하지 않는다 (fork 폭탄 방어 미비 — §7) | 없음 | 없음 |

**계획 (구현 순서)**
1. (P0, 원칙 4·5) 기본 기여량 0% + 할당 시 사전 동의 UI/플래그.
   동의 없이는 materialize·실행 금지.
2. (P1) macOS: `setrlimit` 기반 CPU 시간·메모리 소프트 상한 + 엔진
   프로세스 감시(상한 초과 시 종료). 강제력이 cgroup보다 약함을 명시.
   Windows: Job Objects(CPU rate control, 메모리 상한) 적용.
   두 플랫폼 모두 미지원 기능은 자동 비활성화 + 상태 표시.
3. (P1) `pids.max` 설정 (Linux) + 엔진 자식 프로세스 제한.
4. (P2) 네트워크: 노드별 대역폭 계량·상한 (libp2p bandwidth meter 기반)
   + Relay 전체 대역폭 미터·알림.
5. (P2) Secure Resource Protocol(§6, 별도 문서): 서명된 할당 토큰으로
   자원 범위를 노드에서 강제 검증.

## 3. 격리 — 신뢰되지 않은 작업과 로컬 환경

- **원격 임의 명령 실행 금지**: DAIN 프로토콜에는 명령·셸·파일 접근
  연산이 없다. 노드가 받는 것은 추론 작업(JobRequest: 모델 ID, 메시지,
  토큰 수, RPC 백엔드 목록)뿐이다. `exec.Command` 호출처는 로컬
  하드웨어 조회(`system_profiler`, PowerShell GPU 조회)와 엔진·RPC
  워커 기동뿐이며, 원격 입력이 명령줄에 들어가지 않는다.
- **모델 파일**: SHA-256 검증된 GGUF만 엔진에 넘긴다. 검증 실패 파일은
  서빙되지 않는다.
- **자격증명 격리 (미비)**: 엔진·RPC 워커는 노드와 같은 사용자로
  실행된다. 작업이 로컬 파일(`~/.distributed-ai-node/identity.key`,
  API 키 환경변수)을 읽는 것을 막는 OS 수준 샌드박스가 없다. 현재
  방어는 "작업이 그런 코드를 실행할 경로가 없다"는 프로토콜 설계뿐이다.
  악성 모델 파일이 llama.cpp 취약점을 통해 탈출하면 로컬 파일에 닿을
  수 있다 — 이것이 §6의 샌드박스 계획이 필요한 이유다.
- **계획**: Linux는 네임스페이스(mount/pid/net) + seccomp + 읽기 전용
  모델 디렉토리로 엔진 프로세스를 격리하는 것을 검토한다. macOS는
  sandbox-exec 프로파일, Windows는 AppContainer를 검토한다. 모두
  "지원하지 못하면 자동 비활성화 + 명시" 원칙을 따른다. 단, llama.cpp
  엔진 자체의 GPU·파일 접근 요구 때문에 완전 샌드박스는 엔진 기능을
  제한할 수 있어, 단계적 적용(네트워크 차단 → 파일 쓰기 제한 순)이
  필요하다.

## 4. 위협 모델

공격자를 이렇게 가정한다. 각 항목 뒤에는 현재 방어와 검증 증거를 적는다.

| # | 공격자 | 공격 | 현재 방어 | 검증 |
|---|---|---|---|---|
| T1 | 미등록 외부 노드 | Relay 예약·회선 사용 | allowlist ACL 양단 검사; 빈 allowlist = 거부 | `TestRelayACLDeniesRogue`, `TestRelayDefaultDeniesEmptyAllowlist` |
| T2 | 등록 노드 A | B의 Peer ID로 위장해 ResourceInfo 전송 | V2 ACK 신원 검사 (payload == RemotePeer) | `TestResourceV2RejectsSpoofedPeerID` |
| T3 | 외부 노드 | 거대 메시지로 노드 메모리 고갈 | ResourceInfo 64 KiB 상한 (V1/V2), ACK 4 KiB 상한 | `TestResourceV2RejectsOversizedMessage` |
| T4 | 외부 노드 | ResourceInfo 폭주로 노드 과부하 | Peer별 10개/분 속도 제한 (V1+V2 공유), 거부 기록 | `TestResourceV2RateLimitsAbnormalRequests` |
| T5 | 외부 노드 | Relay 대역폭 고갈 | 회선당 16 MiB, 전체 구조적 상한 512 MiB, 예약 Peer당 4개·IP당 64개 | `TestRelayedStreamLimits` (20 MiB 실패), `TestDefaultRelayLimits` |
| T6 | 키 유출된 노드 | 유출 키로 계속 참여 | allowlist 파일에서 제거 + 릴레이 재시작 (§5) | 절차 문서화; 자동 철회 없음 — 미해결 |
| T7 | 악성 작업 제출자 | 악성 프롬프트·모델로 노드 공격 | 모델 SHA-256 검증; 프롬프트는 텍스트일 뿐 명령이 아님. 샌드박스 없음 — 미해결 | `materialize` 검증; 샌드박스는 계획 |
| T8 | 악성 노드 운영자 | 작업 결과를 거짓 보고·크레딧 부정 수급 | **방어 없음**. 원격 증명 없음; 기여 검증(C/D)은 사용자 결정으로 보류 중 | 미해결 — §6 참조 |
| T9 | 배포 파일 변조자 | 변조된 바이너리·모델 배포 | 릴리스 SHA-256 (`SHA256SUMS.txt`, oracle-setup 검증). 코드 서명 없음 | 부분 — 서명은 미비 (§7) |
| T10 | 네트워크 관찰자 | 트래픽 도청·변조 | libp2p 암호화 전송 (Noise/TLS) | 라이브러리 기본 |
| T11 | 악성 릴레이 운영자 | 트래픽 검열·조작 | 릴레이는 중계만 하고 내용을 검증하지 않음. 종단 간 서명 없음 — 미해결 | 미해결 — 토큰 서명이 부분 완화 |
| T12 | 로컬 사용자 | 실수로 자원 과다 공유 | 기본 0% (수정 중), 명시적 허용만 공유 | P0 수정 대상 |

## 5. 철회 절차 (키 유출 시)

### Relay Peer 권한 철회
1. 릴레이 운영자가 allowlist 파일(`--allow-file`로 지정)에서 유출된
   Peer ID 행을 삭제한다. (파일이 없으면 `--allow` 목록에서 제거하고
   파일을 만든다.)
2. 릴레이를 재시작한다 (`systemctl restart dain-relay` 또는 프로세스
   재기동). 재시작은 모든 회선을 끊으므로, 유출 키의 진행 중 회선도
   함께 종료된다.
3. 검증: 유출 키로 예약을 시도해 `PERMISSION_DENIED`를 확인한다
   (`TestRelayACLDeniesRogue`와 동일한 검사).
4. 해당 노드는 새 identity를 만든다 (`~/.distributed-ai-node/identity.key`
   삭제 후 노드 재시작 → 새 Peer ID 발급). 새 Peer ID를 allowlist에
   추가한다.
5. 릴레이 키가 유출되면 릴레이 Peer ID 자체가 바뀐다: 새 릴레이 키 생성
   후 모든 노드의 `--relay` 주소를 새 주소로 교체해야 한다. 릴레이 키는
   암호화 백업만 하고 저장소에 올리지 않는다.

### 한계 (정직하게 기록)
- 재시작 전까지 유출 키의 기존 회선은 살아 있다. 온라인 철회(재시작
  없는 즉시 차단)는 없다.
- allowlist는 정적 파일이다. 분산 철회 목록(CRL)·만료 기반 토큰이
  없어, 철회는 운영자 수동 절차에 의존한다. Secure Resource Protocol이
  만료·철회 검사를 토큰 검증에 넣는 것을 목표로 한다(§6).

## 6. DAIN Secure Resource Protocol — 요약

상세는 `docs/secure-resource-protocol.md`를 본다. 핵심 한 줄: 사용자가
허용한 자원 사용권을 서명된 토큰으로 표현하고, 노드 자체가 실행 전에
그 토큰을 검증·강제한다. 원격 작업은 토큰 범위를 벗어날 수 없다.

- **보장 가능한 것**: 토큰 서명 검증(Ed25519), 만료·범위·대상 Peer ID
  검사, 모델 해시 일치, OS 강제 상한(cgroup 등)이 있는 곳에서의 상한.
- **보장할 수 없는 것**: 노드 운영자의 거짓 보고(원격 증명 없음),
  GPU 분수 강제, 악성 모델의 엔진 취약점 탈출(샌드박스 없음),
  릴레이 운영자의 트래픽 조작(종단 간 서명 없음).
- **새로운 점 vs 알려진 기술**: 토큰 자체는 새 기술이 아니다
  (Macaroons/Biscuit의 감쇠 가능 capability 토큰이 선행 연구).
  DAIN의 차별점은 capability 토큰 + 노드 로컬 OS 강제 + libp2p
  신원 + 크레딧 장부를 한 프로토콜로 묶는 조합과, 일반 사용자 기기에서
  동작하는 것을 전제로 한 점이다. 이 조합을 최소 구현 + 공격 테스트로
  검증하는 것이 연구의 성패 기준이다 (논문·설계에서 끝내지 않는다).

## 7. 보안상 미해결 + 실제 배포 전 필수 작업

### 미해결 (이번 변경으로 고치지 않은 것)
- 기본 기여량 10% (P0) / 할당 시 자동 모델 다운로드 동의 없음 (P0).
- 서비스 API 공유 키, 노드별 키·철회 없음.
- 온라인 철회 없음 (재시작 필요).
- 엔진 샌드박스 없음 (네임스페이스/seccomp/AppContainer 미구현).
- `pids.max` 미설정, 노드별 대역폭 계량 없음.
- 코드 서명·공증·안전한 업데이트 채널 없음 (SHA-256만 있음).
- 기여 검증(C/D) 없음 — 악성 노드의 거짓 보고를 막을 수 없음.
- 종단 간 작업 서명 없음 — 악성 릴레이의 조작을 막을 수 없음.
- Relay 전체 대역폭 미터·알림 없음 (구조적 상한만 있음).
- libp2p 기본 리소스 매니저를 DAIN이 튜닝·검증하지 않음 (서버 전체
  동시 연결 수의 명시적 상한은 Relay 자원으로만 간접 제한됨).

### 실제 배포 전 필수 작업 (외부 공개 게이트)
1. P0 두 건 수정 (기본 0%, 할당 동의) + 테스트.
2. Relay allowlist에 Mac·테스트 노드 Peer ID만 등록, `--allow-all`
   미사용 확인, TLS 공인 인증서, 전용 VM.
3. Relay 철회 절차 리허설 (유출 키 시나리오로 예약 거부 확인).
4. 엔진 샌드박스 최소안 또는 미적용 시 위험 고지.
5. 코드 서명 또는 최소한 릴리스 SHA-256 검증 절차 문서화.
6. 모니터링: Relay 예약·회선 수, 거부 로그, 대역폭 사용량.

## 8. 검증 원칙

- PASS는 실행 증거가 있을 때만 쓴다. 이 문서의 표에 "검증"이 없는
  항목은 검증되지 않은 것이다.
- 공격 테스트는 모크가 아니라 실제 libp2p 호스트·실제 스트림으로 한다
  (`node/internal/p2p/security_test.go`).
- 보안 수정이 테스트를 깨뜨리면 테스트를 고치는 것이 아니라 수정을
  고친다. 단, 테스트 자체가 보안 결함을 전제로 한 경우(이번
  `TestRelayedStreamLimits`의 512 KiB ResourceInfo 프로브처럼)는
  프로브를 바꾸고 그 이유를 기록한다.
- 이 문서는 코드 변경 시 함께 갱신한다. 문서와 코드가 다르면 코드가
  아니라 문서가 틀린 것으로 취급하지 않는다 — 둘 다 고친다.
