# DAIN Secure Resource Protocol (가칭) — 연구와 실현 가능성 (2026-10-25)

**상태: 연구·설계 문서. 이번 턴에는 구현하지 않았다.** Relay 보안 수정(§5의
근거가 되는 부분)과 별개로, 이 문서는 다음 단계의 구현·검증 구조를 제안한다.
판정 기준은 논문·설계가 아니라 **최소 구현 + 실제 공격 테스트**다.

## 1. 목표

사용자가 허용한 자원 사용권을 노드 자체에서 강제하고, 원격 작업이 그 범위를
벗어날 수 없도록 설계한다. 현재 DAIN의 할당 경로는 신뢰 기반이다: 서비스가
작업을 보내면 노드는 모델을 받아 실행한다. 노드는 할당을 검증하지 않고,
사용자는 할당을 승인하지 않는다 (제품 원칙 4·5 위반). 이 프로토콜은 그
두 빈 곳을 메운다.

- **발급**: 사용자가 허용한 범위(자원 상한·모델·기한·대상 노드)를 서비스가
  서명된 토큰으로 만든다. 토큰은 작업과 함께 노드에 전달된다.
- **검증**: 노드는 실행 전에 토큰 서명·만료·대상 Peer ID·모델 해시·자원
  상한을 검증한다. 하나라도 어긋나면 실행하지 않고 거부한다.
- **강제**: 검증된 상한을 OS 강제 수단(cgroup 등)에 연결한다. 강제할 수
  없는 상한은 토큰에 넣지 않거나 "요청"으로 표시하고, 강제 여부를
  상태로 보고한다.

## 2. 선행 연구와 기존 기술 — 새로운 점과 알려진 기술의 구분

| 기술 | 무엇인가 | DAIN에 주는 것 | DAIN의 새로운 점인가 |
|---|---|---|---|
| Macaroons (Birgisson et al., NDSS 2014) | HMAC 체인으로 만든 감쇠 가능 bearer credential. 보유자는 caveat(제한)를 추가할 수 있고, 제거는 루트 키 없이는 불가능. 권한은 좁아지기만 한다 | 토큰 설계의 핵심 원리: 오프라인 감쇠, caveat 체인 검증 | **아니다**. 원리를 빌린다 |
| Biscuit (Eclipse Biscuit) | 공개키 서명 기반 capability 토큰 + Datalog 정책. 검증자는 루트 공개키만 알면 되고, 감쇠는 오프라인으로 가능 | Macaroons의 공개키 버전. 서비스가 비밀키를 공유하지 않아도 검증 가능 — DAIN의 분산 노드에 적합 | **아니다**. 포맷·라이브러리 재사용을 검토한다 |
| JWT / OAuth scopes | 서명된 토큰 + 스코프. 중앙 발급·검증이 전제 | 익숙한 토큰 형태. 단, 스코프는 문자열 약속일 뿐 노드 로컬 강제와 연결되지 않는다 | 아니다 |
| SPIFFE/SPIRE | 워크로드 신원(URI) + 자동 인증서 발급 | 노드·서비스 신원 관리의 참고. DAIN은 이미 libp2p Peer ID를 신원으로 쓴다 | 아니다 |
| WASI capability model / WebAssembly 샌드박스 | Wasm 모듈에 파일·네트워크 capability를 명시적으로만 부여 | 격리 설계의 참고. 단, llama.cpp는 네이티브 엔진이라 Wasm으로 못 옮긴다 | 아니다 |
| gVisor / Firecracker | 커널·VM 수준 샌드박스 | 엔진 격리의 참고. 일반 사용자 기기의 설치·용량 부담이 크다 | 아니다 |
| TPM / TEE 원격 증명 (SGX/SEV) | 하드웨어가 "이 코드가 실행됐다"를 증명 | 거짓 보고 방지의 유일한 강력한 수단. 단, 일반 사용자 기기(Mac/Windows 보급형)에는 없거나 비활성화돼 있다 | 아니다. DAIN 전제로 쓸 수 없다 |
| eBPF / seccomp / 네임스페이스 | 커널 수준 시스템콜·파일시스템 제한 | Linux 격리 구현 수단 | 아니다. OS 기능을 쓴다 |
| **DAIN의 조합** | capability 토큰 + 노드 로컬 OS 강제 + libp2p 신원 + 크레딧 장부 + 일반 사용자 기기 전제 | — | **조합이 차별점이다.** 어느 한 요소도 새롭지 않지만, 일반 사용자 기기에서 동작하는 분산 AI에 이 조합을 적용하고 최소 구현+공격 테스트로 검증하는 것은 선행 구현이 확인되지 않았다 |

**정직한 평가**: 이 프로토콜의 암호학적 부분은 발명이 아니다. 새로움을
주장한다면 그것은 (a) 자원 상한을 토큰 caveat으로 표현하고 OS 강제와
직결하는 점, (b) 감쇠를 사용자 동의와 연결하는 점(사용자는 토큰을 더
좁혀서 재발급할 수 있다), (c) 검증 실패를 크레딧·평판에 연결하는
운영 설계다. (a)~(c)도 각각 선행 사례가 있으므로, "새로운 프로토콜"이
아니라 "DAIN에 맞는 조합과 검증"으로 부르는 것이 정확하다.

## 3. 보장 가능한 부분과 보장할 수 없는 부분

### 수학·기술적으로 보장 가능한 것
- **토큰 위변조 방지**: Ed25519 서명. 서비스 비밀키 없이는 토큰 내용을
  바꿀 수 없다 (서명 검증은 `crypto/ed25519` 표준).
- **범위 축소만 가능**: Macaroon식 caveat 체인 또는 Biscuit식 블록 추가.
  보유자는 제한을 추가할 수는 있어도 제거할 수는 없다.
- **만료·대상·모델 일치**: 노드가 검증하는 명제는 결정적이다 —
  만료 시간 경과 여부, 토큰의 대상 Peer ID == 자기 Peer ID, 토큰의
  모델 SHA-256 == materialize된 파일의 SHA-256.
- **OS 강제 상한이 있는 곳의 상한**: Linux cgroup v2가 있는 환경에서
  CPU·RAM 상한은 커널이 강제한다. `limits` 패키지가 이미 이 보고를
  정직하게 한다.

### OS·하드웨어 한계 때문에 보장할 수 없는 것
- **노드 운영자의 거짓 보고**: 노드 운영자는 자기 기기에서 무엇이든 할
  수 있다. 실행하지 않고 "실행했다"고 보고하거나, 결과를 조작하는 것을
  막을 수 없다. TEE가 없는 일반 기기에서는 원격 증명이 불가능하다.
  완화책은 결과 재검증(샘플링)·평판·담보뿐이고, 완전한 방지는 아니다.
- **GPU 분수 강제**: 어떤 OS·벤더도 분수 GPU 연산 상한을 제공하지
  않는다. GPU 토큰 상한은 "장치 전체 할당"으로만 강제할 수 있다.
- **악성 모델의 엔진 탈출**: 모델 파일이 llama.cpp 취약점을 이용해
  엔진 프로세스를 탈출하면, OS 샌드박스가 없는 한 로컬 파일에 닿는다.
  토큰은 작업의 *범위*를 검증하지, 모델 파일의 *안전성*을 검증하지 않는다.
- **릴레이 운영자의 조작**: 릴레이가 토큰·작업을 바꿔치기하면 노드는
  그것을 알 수 없다. 토큰이 작업 본문에 서명돼 있으면 릴레이는 내용을
  바꿀 수 없지만, 트래픽을 버리거나 지연시키는 것은 막을 수 없다.
- **사용자 기기의 물리적 접근**: 기기를 가진 자는 키를 읽을 수 있다.
  키 유출 시 철회 절차(allowlist 파일 + 재시작)가 유일한 방어다.

## 4. 토큰 설계 (제안)

발급자는 서비스(중앙)이며, 검증자는 각 노드다. 노드는 서비스 공개키 하나만
알면 된다. 토큰은 작업(JobRequest)과 함께 전달된다.

```
AssignmentToken {
  version:   1
  job_id:    string          // 작업 식별자 (재사용 방지)
  node_id:   PeerID          // 대상 노드 — 자기 ID가 아니면 거부
  model_id:  string
  model_sha256: hex          // materialize 검증과 동일한 해시
  cpu_percent: int           // 0 = 상한 없음이 아니라 "할당 없음" (거부)
  ram_bytes:   int64
  storage_bytes: int64       // 이 작업이 쓸 수 있는 모델·캐시 용량
  max_tokens:  int
  network_bytes: int64       // 이 작업의 송수신 상한 (0 = 네트워크 없음)
  expires_at:  RFC3339
  issued_at:   RFC3339
  caveats:    []string       // 추가 제한 (감쇠용, 예: "no_network")
  signature:  Ed25519(발급자 비밀키, 위 필드들의 canonical JSON)
}
```

**검증 순서 (노드, 실행 전 — `executor.HandleStream` 진입 시)**
1. 서명 검증 (실패 → 거부 `bad_token_signature`).
2. `expires_at` 경과 검사, `job_id` 재사용 검사 (본 적 있는 job_id는 거부 — 재전송 공격 방지. 재사용 목록은 메모리 + TTL).
3. `node_id` == 자기 Peer ID 검사.
4. `model_sha256` == 로컬 모델 파일 해시 검사 (없으면 materialize 후 검사).
5. 자원 상한을 `limits.Apply`에 연결할 수 있는지 검사. 강제 불가 상한이
   있으면 거부하거나(엄격 모드) 경고 상태로 실행(관대 모드 — 기본은 거부).
6. 전부 통과하면 실행. 실행 중 상한 초과는 OS가 차단하고, 노드는 실패를
   보고한다.

**감쇠 (사용자 동의와 연결)**: 사용자는 토큰에 caveat를 추가해 더 좁은
토큰을 만들 수 있다 (예: `max_tokens`를 100으로). 감쇠된 토큰은 발급자와
다시 통신하지 않고 만들 수 있다 (Macaroon식). 노드는 원본 서명과
caveat 체인을 함께 검증한다.

**철회**: 토큰은 짧은 만료(예: 10분)로 철회 창을 줄인다. 장기 철회는
서비스가 발급을 중단하는 것으로 처리한다. 노드 키 철회는 Relay allowlist
절차와 동일하다.

## 5. 최소 구현 계획 (다음 단계 — 이번 턴에 구현하지 않음)

구현 범위를 의도적으로 작게 잡는다. 목표는 "동작하는 토큰 검증 + 공격
테스트"이지, 완전한 프로토콜이 아니다.

1. `node/internal/token/` 패키지: 토큰 구조체, canonical JSON, 서명
   생성·검증, 만료·대상·재사용 검사. 외부 의존성 없이 표준 라이브러리만
   사용한다 (Ed25519는 `crypto/ed25519`).
2. `executor.HandleStream` 진입 시 토큰 검증 훅: 토큰이 없으면 거부
   (엄격 모드). 기존 토큰 없는 경로(v0.10-alpha 호환)는 플래그로만 허용하고
   기본은 거부한다.
3. 서비스 발급 경로: 작업 배정 시 토큰을 함께 서명해 전달한다.
   (서비스 변경이므로 별도 승인·배포 창이 필요하다 — 이번 턴의 범위를
   넘는다.)
4. `limits.Apply`와 토큰 상한 연결: 토큰의 `cpu_percent`·`ram_bytes`를
   엔진 cgroup에 적용하고, 적용 결과를 작업 결과에 포함한다.
5. 공격 테스트 (`node/internal/token/*_test.go` + executor 통합 테스트):
   - 변조된 토큰 (서명 불일치) → 거부
   - 만료된 토큰 → 거부
   - 다른 노드 대상 토큰 → 거부
   - 모델 해시 불일치 토큰 → 거부
   - 재사용된 job_id (재전송) → 거부
   - 상한 초과 작업 (CPU·RAM) → OS 강제 또는 거부
   - 감쇠된 토큰 (더 좁은 범위) → 허용, 원본보다 넓은 재발급 시도 → 거부

**구현하지 않는 것 (이 단계에서)**: Biscuit/Datalog 엔진 도입 (토큰 검증에
Datalog이 필요할 만큼 정책이 복잡하지 않다), TEE 증명, 분산 철회 목록,
평판 시스템. 이들은 토큰 검증이 동작한 뒤에 검토한다.

## 6. 검증 기준

이 프로토콜은 다음이 모두 충족될 때 "검증됐다"고 말한다.
- 최소 구현이 위 공격 테스트 7개를 전부 통과한다.
- 공격 테스트가 실제 토큰·실제 서명·실제 cgroup으로 수행된다 (모크 금지).
- 보장할 수 없는 부분(§3)이 문서와 사용자 안내에 명시돼 있다.
- 토큰 검증 실패가 로그·크레딧에 기록되고, 반복 실패 노드는 할당에서
  제외되는 운영 절차가 있다.
